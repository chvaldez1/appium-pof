# Testing conventions

## Reading and writing a test

WebdriverIO E2E files use `.spec.ts` and Mocha's `describe()`/`it()`. The asynchronous callback passed to `it()` is the test body. WebdriverIO creates the session and executes the `before` hook in `src/setup/session-hooks.ts` first. Node unit tests use `.test.ts` under `tests/unit/`.

Put a test under `native/` when it exercises native controls, `hybrid/` when it crosses native and embedded web contexts, or `mobile-web/` for browser execution. Keep iOS-only journeys under an `ios/` directory. The app smoke test remains cross-platform, and the Safari setup spec also serves desktop Safari. Register each new E2E spec in `config/specs.ts`; do not broaden default discovery to include purchases.

Specs describe the scenario and assert its outcome. Use flows for multi-screen navigation and page objects for locators and actions. Pass scenario data and credentials explicitly. Avoid putting APIs, credentials, fixtures, or session setup into screen objects. Preserve platform-specific implementations where native behavior differs.

Use lazy selector getters, meaningful action names, PascalCase classes, camelCase functions, and kebab-case module names. Prefer condition-based waits when adding interactions. Do not change a proven selector just to match a style preference during a structural migration.

## Imports

Use the aliases in `tsconfig.json`:

```ts
import { preparePublicPurchase } from '@flows/buyer/ios/public-purchase.ts';
import { iosLoginPage } from '@screens/native/ios/auth/login.ts';
import { getPurchaseItems } from '@api/purchase-invoices.ts';
import { adultTicketPurchase } from '@data/purchase-scenario.ts';
import { timeoutMs } from '@config/test-settings.ts';
```

Other aliases are `@support/`, `@setup/`, `@scripts/`, and `@tests/`. Do not add forwarding modules or deep relative imports to conceal a module's ownership. Relative URLs used to locate files such as `.env.local` are asset paths, not module imports.

## Purchase inputs and environment variables

`process.env` is Node's interface to the current process environment. It is appropriate for credentials and runtime options; it is not a fixture-file reader. Values are strings or absent, so `DRY_RUN === '1'` is an explicit boolean convention.

The existing purchase command follows this path:

```text
npm run test:public[:dry-run]
  → scripts/run-with-playwright-fixtures.ts public
  → local settings / shell overrides / literal Playwright account fixtures
  → generate a unique guest email and spawn WebdriverIO with environment values
  → config/purchase-settings.ts validates the handoff
  → tests/hybrid/checkout/ios/public-purchase.spec.ts
```

The bridge passes `PUBLIC_GUEST_EMAIL`, `PUBLIC_GUEST_NAME`, `PUBLIC_GUEST_PHONE`, `PUBLIC_RUN_TAG`, and private Organizer credentials. Organizer credentials are used for backend reads; the buyer checks out as a guest. `.env.local` stays ignored. Fixed Event, address, and approved Stripe test-card inputs live under `src/data/`; the guest email is generated by a small function under `src/data/factories/`.

The purchase test reads as:

1. Validate the scenario and guest inputs; reject an existing order for that email.
2. Prepare a new recovery directory; navigate to checkout and fill the inputs.
3. End a dry run before submission.
4. Save the recovery marker, then submit payment once.
5. Read and verify the invoice, purchased item, and issued ticket.
6. Match the app's confirmation to the saved transaction.

`src/flows/buyer/ios/public-purchase.ts` coordinates native controls and the payment WebView. `src/api/purchase-invoices.ts` owns HTTP reads. `src/flows/purchase/verify-purchase.ts` owns reusable scenario checks and polling. `src/support/artifacts/run-artifacts.ts` owns recovery file operations. The spec retains the scenario's assertions and the order of these operations.

Use the named purchase command so `PURCHASE_RUN=1`, the extended timeout, reset behavior, and sensitive logging are applied together. Direct spec invocation still requires the existing runtime inputs and run flags. Do not print card numbers, CVCs, passwords, or private account values in logs or shared artifacts.

## Validation and reporting

Run `npm run check` before sharing changes. It runs one check at a time. Use `npm run test:discovery` for device-free discovery validation and named commands for actual smoke/journey execution.

Report validation precisely: static checks, execution without payment, or a completed order with an issued ticket. Unit tests and discovery are not evidence that a simulator journey passed. If a purchase outcome is uncertain, read the saved order through recovery before considering another attempt. Existing app crashes and missing builds remain blockers to their affected journeys.
